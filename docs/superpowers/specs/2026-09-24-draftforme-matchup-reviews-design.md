# DraftForMe Matchup Reviews Design

Date: 2026-09-24

## Summary

Let signed-in players with a nickname leave a community opinion on a lane matchup (which champion wins, and why) and read others': one vote per account per matchup, a flat discussion of comments, up/downvotes on other people's comments, and a report button. A player cannot react to their own comment: the UI shows its score read-only, and the database policy refuses the write as well. This is the third and last of the three pieces of work announced in the legal-pages and accounts specs. It ships with updates to the privacy policy and terms of use in the same piece of work, as promised in both.

Reviews are read-only input for the player: **they do not feed `src/lib/recommendation/`.** The engine keeps scoring purely from `champion_stats` and `counter_relations`, both sourced from OP.GG. Wiring community votes into the score is a real product change with its own trade-offs (weight, abuse resistance, cold start) and would need its own spec.

This spec records what was built on `feat/matchup-reviews`, including the decisions taken during implementation and review, not only the ones taken before the plan.

## Why

- **The two previous pieces of work exist for this one.** Accounts give reviews an author to attribute a vote to, rate-limit, and moderate. Legal pages already say reviews are coming.
- **The verdict comes first, the discussion second.** Each matchup page leads with the vote (who wins this lane); below it, players discuss the matchup in a flat list of comments. The owner chose an open discussion over one review per account, so volume is capped by a database-side rate limit rather than by the data model.
- **Nothing today identifies "a matchup."** The engine's `counter_relations` table is directional and scoped by role (`champion_id` is beaten by `countered_by_champion_id` in `role`), which is right for scoring but wrong for a community page: "Darius top vs Garen top" is one conversation, not two.
- **Every rule that matters lives in the database, not only in the Server Actions.** Anyone with a session can call Supabase directly with the anon key, so ownership, timestamps, the rate limit, the nickname requirement and the no-self-reaction rule are all enforced by RLS policies or triggers; the Server Actions repeat them only to give a French message or a redirect instead of a raw refusal.

## Decisions

| Question | Decision |
|---|---|
| What a "vote" is | A single choice among three: **this champion wins**, **the other champion wins**, **égalité**. Rejected: a 1-5 difficulty/rating scale (rating what, exactly, is ambiguous without a fixed reference champion, and doesn't map to a simple aggregate; a three-way pick mirrors `counter_relations`' own vocabulary and is one tap) |
| Matchup key | **`role` plus an unordered champion pair**, canonicalized as `champion_low_id < champion_high_id` (lexicographic on `champions.id`, already a stable lowercase slug) so "Darius vs Garen" and "Garen vs Darius" are the same row. A `check` constraint enforces the order; `role` has its own `check (role in ('top', 'jungle', 'mid', 'adc', 'support'))` on both tables, exactly `ROLES` in `src/lib/draft/roles.ts` (a comment in the migration says to keep the two in step), so no row can be filed under a role the site never shows. `src/lib/matchup/key.ts` canonicalizes both ends before every query or write, so the app never has to try both orders. Both champions share `role`: that is what the existing seed data means by "role" on a counter pair (`scripts/build-seed-data.mjs` writes one `counter_relations` row per role from OP.GG's per-role counters list), and it is also the only matchup a viewer of the draft tool can act on directly (their lane) |
| No shared "matchup" table | The three (`role`, `champion_low_id`, `champion_high_id`) columns are repeated on `matchup_votes` and `matchup_comments`, each with its own `check` for the canonical order, instead of a normalizing dimension table. This matches the existing schema's style (`champion_stats`, `matchups`, `builds` each repeat their own composite key rather than sharing one), at the cost of repeating three columns and two checks in two tables |
| Where reviews live in the UI | **Confirmed by owner.** A dedicated page per matchup (`/duel/[role]/[a]-vs-[b]`, canonical order in the URL) holding the vote buttons, the comment list and form, and the report button; the draft board's `Verdict` panel gains a small "Avis de la communauté" link next to the counter explanation, pointing at the matchup between the recommended champion and the enemy on the drafting role. `Verdict` takes two optional props, `role` and `enemyChampionId`, which `draft-board.tsx` fills with `draft.yourRole` and the existing `directOpponent(draft)`; the link is hidden unless both are known and the enemy is not the recommended champion itself. Rejected: building the whole review UI inline in the draft board -- that panel already re-renders on every pick, and a form plus a list plus pagination would compete for the space the recommendation itself needs; a dedicated page also gives reviews a permalink, which sharing and moderation both want |
| Comments: one per account per matchup, or open discussion | **Confirmed by owner: open discussion.** An account may post several comments on the same matchup. The list stays **flat**: no replies or threading in v1, which keeps rendering, sorting and moderation simple. A comment is independent of its author's vote (no "voted X" badge), so changing a vote never rewrites what a comment appeared to say. Rejected: one comment per account per matchup (the recommended default, turned down by the owner) |
| Comment length, edit, delete; server-owned columns | 3 to 500 characters after trimming, plain text (rendered as text, never `dangerouslySetInnerHTML` -- no HTML, no markdown, no links rendered as links). Editable at any time by its author, with a "modifié le ..." marker; deletable at any time by its author (hard delete: the row and its reactions and reports cascade). **The database owns every column but `body`.** On insert, the rate-limit trigger stamps `created_at` and `updated_at` with `now()`, whatever the client sent. On update, `lock_matchup_comment_columns()` restores `id`, `created_at`, `role`, `champion_low_id` and `champion_high_id` from the old row, and restores `user_id` unless the new value is `null` (the `on delete set null` foreign key anonymizes through an UPDATE that must pass); it bumps `updated_at` only when `body` actually changes, so anonymization never shows as an edit. The app never sends a timestamp, and `edited` is simply `updated_at <> created_at`. Why: a client with its own session could otherwise backdate a comment out of the rate-limit windows, move it to another matchup, hand it to another account, or fake a "modifié" date. **Votes are locked the same way:** `stamp_matchup_vote()` sets both timestamps on insert, and `touch_matchup_vote()` restores `id`, the matchup key, `user_id` and `created_at` on update and sets `updated_at = now()`, so a vote can change its `choice` and nothing else (`user_id` is not nullable there, since votes cascade on account deletion, so no anonymizing UPDATE needs to pass) |
| Up/downvote on comments and sorting | One reaction per account per comment, `for` or `against`, upserted on the unique `(comment_id, user_id)` (changing your mind moves the reaction, it doesn't add a second one). **Not on one's own comment:** the comment list shows the author read-only counts instead of buttons, and the reactions policy's `with check` refuses a row whose comment belongs to the caller; a comment anonymized by account deletion (`user_id` null) matches no caller and can still be reacted to. Reactions are other players' opinion of a comment, so a self-upvote would make the score say something false. Sort: score (`for` minus `against`) descending, ties broken by `created_at` descending, done in `getComments` (`src/lib/matchup/reviews.ts`) **before** pagination, so "Voir plus" pages through the sorted list rather than sorting each page on its own. No sort toggle; "Voir plus" is a plain link carrying `?offset=` (20 comments per page, `src/lib/matchup/pagination.ts`), no client-side fetching. Reactions are embedded in the comments query through the foreign key, so every comment carries all of its reactions. The top-level comment rows are one query and therefore capped by PostgREST's `max_rows` (1000) per matchup: accepted at this project's scale, and the first thing to revisit (a database-side sort, a view or an RPC) if one matchup ever approaches it |
| Showing vote and reaction numbers vs an invented aggregate | Raw counts are always shown as-is (an exact count is a fact, not an estimate, so the "never show an invented number" rule does not ask to hide it). What is hidden below a threshold is a derived reading of those counts: the matchup page does not show a percentage-style verdict line until the matchup has **at least 5 votes**; below that it shows only the raw counts. A percentage computed from one or two votes reads as false confidence, exactly the kind of misleading number the rule is written against, even though the inputs are real. At 5 votes and above, the line reads "X % pensent que <champion> gagne (N votes)" or "X % pensent que c'est une égalité (N votes)" when one choice strictly leads; **when two or three choices share the top count, it reads "Avis partagés (N votes)"** rather than naming one leader arbitrarily. Vote counts are computed by the database (`count: "exact", head: true`, one query per choice), so they are exact however many votes a matchup has and are not truncated by `max_rows` |
| Rate limiting and anti-stuffing | No CAPTCHA or IP throttling in v1. Votes and reactions are capped structurally (one vote per account per matchup, one reaction per account per comment), enforced by Postgres unique constraints and RLS on `auth.uid() = user_id`. Comments, since an account may post several, are capped by the **`before insert` trigger `enforce_comment_rate_limit()`**: at most **3 comments per account per matchup in 10 minutes** and **20 per account across the site in 24 hours**; beyond that the insert raises `comment_rate_limited` with `errcode 'P0001'`, and `postComment` maps it to its French message only when both the code and the message match, so no other `P0001` is mistaken for it. The limit lives in the database, not the Server Action, so a client calling Supabase directly with its own session hits it too. The trigger takes a per-author `pg_advisory_xact_lock(hashtext(user_id))` before counting, so concurrent inserts by one author are serialized and a burst cannot slip past the cap; it then stamps `created_at`/`updated_at` itself, because the windows trust `created_at` and a backdated insert would otherwise fall outside every window. The two limits are literals inside the function (not a settings table), starting values rather than measured ones, tuned by a later migration. The windows count existing rows, so **deleting a comment frees its slot**: accepted, since posting and deleting in a loop leaves nothing visible behind. Multi-accounting (many OAuth logins voting the same way) is an accepted residual risk, the same posture as account creation itself at this project's scale -- noted, not solved here |
| Posting requires a nickname | Reuses the accounts spec's stated intent ("Chantier 3 will require a nickname before posting"). Enforced twice: **in the Server Actions**, where every action (vote, comment, edit, delete, reaction, report) goes through `requireNicknamedUser`, which redirects a signed-out visitor to `/connexion?next=...` and a signed-in user without a nickname to `/compte/pseudo?next=...` (and returns the generic error, not a redirect, when the profile cannot be read, since sending someone to choose a nickname they already have would be false); and **in the insert policies of `matchup_votes` and `matchup_comments`**, which require a `profiles` row with a non-null `display_name` for the caller (`profiles_select_own` from 0001 lets the subquery read the caller's own row; `castVote`'s upsert goes through the insert check even when it ends up updating). Reactions and reports are nickname-gated by the Server Actions only. On the page, a signed-in user without a nickname sees a « Choisissez un pseudo » link (back to the current page, `offset` included) instead of the comment form, because posting would redirect and lose the typed text; a signed-out visitor sees a « Connectez-vous » link |
| Public readability of votes and reactions | **Confirmed by owner on 2026-09-24:** `matchup_votes` and `matchup_comment_votes` stay readable by anyone, `anon` included (`select using (true)`), with their `user_id` column, and the legal pages say so. Combined with the nickname lookup below, anyone can tie a commenter's votes and reactions to their nickname. Accepted rather than hidden behind an aggregate view because the page needs the caller's own vote and reactions and the counts, and a vote is a public opinion on a public page; the privacy policy states it plainly instead. **Nicknames** come from a new view, `public_profiles (user_id, display_name)`: `profiles` RLS is own-row only (0001), and `matchup_comments.user_id` references `auth.users`, not `profiles`, so there is no foreign key for PostgREST to embed a nickname through. The view is a plain view running with its owner's rights (deliberately not `security_invoker`), which is what lets it read past `profiles`' own-row policy, so it exposes exactly two columns and only the rows of accounts that have a nickname and at least one comment -- it cannot enumerate every account's nickname, and `default_region`, `default_role` and the timestamps stay private. Grants: `revoke all` then `grant select` to `anon` and `authenticated`. Supabase's database advisor is expected to flag it as a "security definer view"; that warning is the intended trade-off, not a defect. `getComments` only looks up the authors of the page being shown, so the `.in()` list holds at most 20 ids |
| Withdrawing a vote or a reaction | **Change, not withdraw, from the site.** The vote panel and the reaction buttons set a value; there is no "retirer" control in v1, so a player who has voted can move their vote but not take it back through the site. The database would allow it (the vote and reaction policies include `delete` on one's own rows), but no action exposes it. The legal pages say so and point to the « Vos droits » section for an erasure request short of deleting the account |
| Reporting flow | A report is `(comment_id, reporter_user_id, reason)`, `reason` one of `spam`, `insultant`, `hors_sujet`, `autre`, unique per `(comment_id, reporter_user_id)` (one report per person per comment). Insert-only for `authenticated` (`with check (auth.uid() = reporter_user_id)`); **no select policy for `anon` or `authenticated`** -- not even the reporter can list reports back, which keeps a reporter's identity from leaking through the API. **The migration also runs `revoke select on matchup_comment_reports from anon, authenticated`**, because 0003 ends with `alter default privileges in schema public grant select on tables to anon, authenticated`, which applies to every table created afterwards and would otherwise hand out the table-level `select` this decision depends on not existing. Rows are read only by the owner, outside RLS, through the Supabase dashboard (the `postgres` role bypasses RLS). The report button appears only on other people's comments; a report changes nothing visible, so its action does not revalidate the page |
| Who moderates, and how | **Confirmed by owner: the owner alone, through the Supabase dashboard's table editor or SQL editor** -- the same posture as `delete_my_account()`'s note in the accounts spec ("no service-role key on the server"). No admin flag, no in-app moderation UI, no notification e-mail (a digest needs a sender, rejected here for the same reason magic-link sign-in was rejected in the accounts spec). The owner checks `matchup_comment_reports` manually. A comment is removed with a plain delete; there is no `hidden` column and no soft-hide state, so there is nothing for RLS to filter and no admin-only read policy to write |
| Hide a comment automatically after N reports | **Confirmed by owner: no**, for v1. Auto-hiding on report count is easy to brigade (a handful of accounts silences a comment nobody moderated), and the expected volume is low enough that manual review is realistic. Revisit if abuse actually shows up |
| Votes and comments on account deletion | **Confirmed by owner: votes cascade-delete** (`on delete cascade`, same as `champion_pool_entries`) -- a vote has no value once orphaned, and removing it keeps the aggregate honest. Reactions and reports cascade too. **Comments are anonymized, not deleted** (`user_id` nullable, `on delete set null`, text kept, author shown as "Utilisateur supprimé") -- the comment is the content other players came to read. `delete_my_account()` (migration 0004) needs no change: the new tables' own `on delete cascade`/`set null` foreign keys do the work when `auth.users` loses the row, and `lock_matchup_comment_columns()` lets the null through without marking the comment edited. The legal pages tell players to delete their comments before their account if they want them gone, since afterwards only the publisher can |
| Scoring | **Unchanged.** No table here is read by `src/lib/recommendation/engine.ts` or `counter.ts`; the recommend API and `load-example.ts` keep their identical `champion_stats` and `counter_relations` queries. Wiring votes into scoring is explicitly out of scope and would need its own spec |

## Design

### Migration `0005_matchup_reviews.sql`

- `matchup_votes`: `id uuid pk`, `role text not null check (role in ('top', 'jungle', 'mid', 'adc', 'support'))`, `champion_low_id text not null references champions(id) on delete cascade`, `champion_high_id text not null references champions(id) on delete cascade`, `user_id uuid not null references auth.users(id) on delete cascade`, `choice text not null check (choice in ('low', 'high', 'even'))` (`choice` names the winner by its canonical slot, not by id, so the row stays meaningful regardless of which champion ended up `low` or `high`), `created_at`, `updated_at`. `check (champion_low_id < champion_high_id)`. `unique (role, champion_low_id, champion_high_id, user_id)`.
- `matchup_comments`: `id uuid pk`, the same `role` check and champion columns, `user_id uuid references auth.users(id) on delete set null` (nullable: anonymized on account deletion), `body text not null check (char_length(body) between 3 and 500)`, `created_at`, `updated_at`. `check (champion_low_id < champion_high_id)`. No uniqueness on the author: several comments per account per matchup are allowed.
- `matchup_comment_votes` (reactions): `id uuid pk`, `comment_id uuid not null references matchup_comments(id) on delete cascade`, `user_id uuid not null references auth.users(id) on delete cascade`, `value text not null check (value in ('for', 'against'))`, `created_at`. `unique (comment_id, user_id)`.
- `matchup_comment_reports`: `id uuid pk`, `comment_id uuid not null references matchup_comments(id) on delete cascade`, `reporter_user_id uuid not null references auth.users(id) on delete cascade`, `reason text not null check (reason in ('spam', 'insultant', 'hors_sujet', 'autre'))`, `created_at`. `unique (comment_id, reporter_user_id)`.
- Trigger functions, all with `set search_path = ''`:
  - `enforce_comment_rate_limit()`, `before insert on matchup_comments` (trigger `matchup_comments_rate_limit`): `security definer`, so the counts see every row regardless of the caller's RLS (same hardening as `delete_my_account()`); takes the per-author advisory transaction lock, counts the author's comments on the same matchup in the last 10 minutes and site-wide in the last 24 hours, raises `comment_rate_limited` (`P0001`) past 3 or 20, then sets `created_at` and `updated_at` to `now()`.
  - `lock_matchup_comment_columns()`, `before update on matchup_comments` (trigger `matchup_comments_lock_columns`): restores `id`, `created_at`, the matchup key, and `user_id` unless it becomes null; bumps `updated_at` only when `body` changes, otherwise keeps the old value.
  - `stamp_matchup_vote()`, `before insert on matchup_votes` (trigger `matchup_votes_stamp`): sets both timestamps to `now()`.
  - `touch_matchup_vote()`, `before update on matchup_votes` (trigger `matchup_votes_touch`): restores `id`, the matchup key, `user_id` and `created_at`; sets `updated_at = now()`.
- RLS enabled on all four tables. Policies:
  - `matchup_votes`: `matchup_votes_read_all` (`select using (true)`); `matchup_votes_insert_own` (`with check (auth.uid() = user_id and exists (a profiles row for auth.uid() with display_name not null))`); `matchup_votes_update_own` (`using` and `with check` on `auth.uid() = user_id`); `matchup_votes_delete_own` (`using (auth.uid() = user_id)`). Split per command, rather than one `for all`, so only insert carries the nickname check.
  - `matchup_comments`: `matchup_comments_read_all` (`select using (true)`); `matchup_comments_insert_own` (same shape as the vote insert policy, nickname check included); `matchup_comments_update_own` and `matchup_comments_delete_own` on `auth.uid() = user_id`. No policy clears `user_id` -- that only happens through the `on delete set null` foreign key when the account itself is gone.
  - `matchup_comment_votes`: `matchup_comment_votes_read_all` (`select using (true)`); `matchup_comment_votes_all_own` (`for all using (auth.uid() = user_id) with check (auth.uid() = user_id and not exists (a matchup_comments row with id = comment_id and user_id = auth.uid()))`), which refuses a reaction on one's own comment on insert and update.
  - `matchup_comment_reports`: `matchup_comment_reports_insert_own` (`insert with check (auth.uid() = reporter_user_id)`) only. No `select` policy at all.
- Table privileges: `select, insert, update, delete` on `matchup_votes`, `matchup_comments`, `matchup_comment_votes` to `authenticated`; `select` on the same three to `anon`; `insert` on `matchup_comment_reports` to `authenticated`; then `revoke select on matchup_comment_reports from anon, authenticated` to undo 0003's default privileges (see Decisions).
- View `public_profiles`: `select p.user_id, p.display_name from profiles p where p.display_name is not null and exists (a matchup_comments row by p.user_id)`. Plain view (owner's rights, not `security_invoker`); `revoke all on public_profiles from anon, authenticated`, then `grant select` to both.
- Indexes: `matchup_votes_lookup_idx (role, champion_low_id, champion_high_id)`, `matchup_comments_lookup_idx (role, champion_low_id, champion_high_id, created_at desc)`, `matchup_comments_author_idx (user_id, created_at desc)` (serves the rate-limit trigger and the `public_profiles` existence check), `matchup_comment_votes_comment_idx (comment_id)`.

Exports the `MatchupKey` type (`{ role, championLowId, championHighId }`), `matchupKey(championAId, championBId, role)` (canonicalizes; throws when both ids are equal), `pairSegment(key)` (`<low>-vs-<high>`), `parsePairSegment(segment)` (null unless exactly two non-empty ids already in canonical order), `matchupHref(championAId, championBId, role)` (the typed `Route` to `/duel/<role>/<low>-vs-<high>`) |

| `src/components/draft/matchup/comment-list.tsx` | Renders comments in the order given (sorting is `reviews.ts`'s job); author nickname or "Utilisateur supprimé"; dates in `Europe/Paris` so server and client agree; "modifié le ..." marker; reaction buttons on other people's comments, read-only counts on one's own; edit and delete on one's own; the report button on other people's |
| `src/components/draft/matchup/comment-form.tsx` | The comment form; controlled textarea so a failed post (rate limit, length) keeps the typed text, cleared only after a successful post |
| `src/components/draft/matchup/report-button.tsx` | "Signaler", then the four reasons; remounted on each opening so a stale error never reappears; focus returns to "Signaler" on cancel |
| `src/components/draft/verdict.tsx` | Optional props `role?: Role` and `enemyChampionId?: string \| null`; adds the "Avis de la communauté" link built with `matchupHref` when both are known and differ from the recommended champion |
| `src/components/draft/draft-board.tsx` | Passes `role={draft.yourRole}` and `enemyChampionId={directOpponent(draft)}` to `Verdict` |
| `supabase/migrations/0005_matchup_reviews.sql` | See above |
| `src/lib/supabase/types.ts` | The four tables and the `public_profiles` view |
| `src/components/legal/privacy-policy.tsx`, `terms-of-use.tsx` | Legal updates below |

Every file above except the migration, the types and `draft-board.tsx` has its test next to it (`*.test.ts(x)`). Components live under `src/components/draft/matchup/`, not a new top-level `src/components/matchup/`, since the review pages belong to the draft tool's scope.

`[pair]` is a single segment, `<low>-vs-<high>` in canonical order; a non-canonical or unknown pair returns a 404 rather than a redirect, to keep the route simple and the page cacheable per exact URL. `champions.id` never contains a hyphen, so `-vs-` is an unambiguous separator.

### Legal updates (same piece of work)

- **Privacy policy**: the "Données traitées" intro now points to both the « Compte » and « Avis » sections. The former "Évolutions à venir" section is replaced by a new **« Avis »** section, which states:
  - what is stored, each tied to the account: the vote choice, the text of comments (several per matchup allowed), reactions (for or against) on other players' comments, and the reason of any report, which only the publisher can read;
  - that the nickname is shown publicly next to comments, and that votes and reactions are public, stored with the account's technical identifier which anyone can read, and can therefore be linked to the nickname of someone who has commented;
  - purpose (publishing community opinions on matchups, and moderation) and legal basis (performance of the service requested by voting, commenting or reacting, GDPR art. 6.1.b; the publisher's legitimate interest for reports);
  - retention, split: votes, reactions and reports at the latest until the account is deleted; comments until their author deletes them or the publisher removes them, including after the account is deleted;
  - that while the account exists its holder can edit or delete comments and change a vote or a reaction, but the site does not let them withdraw a vote or a reaction, only change it; erasing one without deleting the account is a request to the publisher (« Vos droits »);
  - what account deletion does: votes, reactions and reports are deleted with it; comments stay visible, detached from the account, with the author shown as « Utilisateur supprimé »; whoever wants them gone should delete them before deleting the account, since afterwards only the publisher can.
- **Terms of use**: « Accès au service » now says an account is needed to give an opinion on matchups. ### Errors

| Case | Behaviour |
|---|---|
| Not signed in, tries to vote, comment, react or report | The page offers a « Connectez-vous » link instead of the comment form; a vote, reaction or report submitted anyway redirects to `/connexion?next=...` |
| Signed in, no nickname | The page shows the « Choisissez un pseudo » link instead of the comment form; any action redirects to `/compte/pseudo?next=...`. A direct insert into `matchup_votes` or `matchup_comments` is refused by RLS |
| Signed in, profile cannot be read | "Une erreur est survenue. Réessayez plus tard." (no redirect to choose a nickname the user may already have) |
| Comment body outside 3-500 characters (after trimming) | "Le commentaire doit faire entre 3 et 500 caractères.", without touching the database; the textarea also carries `minLength`/`maxLength` |
| Invalid form fields (non-canonical key, unknown choice, reaction value or reason, missing comment id) | Generic French error, without touching the database |
| Duplicate vote or reaction | No error path: both are upserts on the table's unique columns, so the vote or reaction moves; Postgres never raises `23505` for them |
| Reaction on one's own comment | Not offered by the UI; a direct write is refused by the reactions policy, and the action would return the generic error |
| Duplicate report (Postgres `23505`) | "Vous avez déjà signalé ce commentaire." |
| Comment rate limit hit (`P0001` with message `comment_rate_limited`) | "Vous commentez trop vite. Réessayez dans quelques minutes." The typed text stays in the form. Any other error is the generic one |
| Unknown role, non-canonical `[pair]`, or a champion id missing from `champions` | 404 |
| Editing or deleting someone else's comment | The update or delete is scoped to `id` and the caller's `user_id`, and RLS agrees; no row comes back, so the action returns the generic French error |
| `?offset=` invalid | First page. Past the last comment: "Il n'y a pas d'autre commentaire à afficher." with a link back to the first page |
| Supabase unreachable | Champions unreadable: header, footer and the generic French error only (not a 404, the matchup may exist). Votes or comments unreadable: that section alone shows "Une erreur est survenue. Réessayez plus tard.", never zero counts or an empty discussion. A failed write shows the same message in its form. Page metadata falls back to a generic title |
