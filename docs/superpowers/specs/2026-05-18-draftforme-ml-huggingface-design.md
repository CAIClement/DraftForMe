# DraftForMe ML + Hugging Face Design

Date: 2026-05-18

## Summary

DraftForMe will add a separate machine-learning pipeline that learns to recommend League of Legends champions from three signals: player profile, current draft context, and meta data.

The first version will train a tabular ranking model from expert labels generated by the existing recommendation engine. Later versions will enrich the training data with real match outcomes from Riot or other cached sources. The model will be published to Hugging Face with a Gradio Space so it can be tested independently from the main Next.js app.

## Goals

- Train a first custom recommendation model for champion suggestions.
- Use a hybrid input strategy: player profile, draft state, and meta statistics.
- Start with expert labels from the current recommendation engine to avoid waiting for a large match dataset.
- Keep the ML pipeline separate from the Next.js app so it can be trained, tested, and published independently.
- Publish a usable Hugging Face Space for interactive testing.
- Preserve explainability by returning readable factors alongside ranked champions.
- Leave the current TypeScript recommendation engine in place until the ML model is validated.

## Non-Goals

- Do not replace the production recommendation route in the first ML version.
- Do not train a large language model or transformer for the first version.
- Do not require live Riot or OP.GG scraping during inference.
- Do not claim the model is better than the expert engine until evaluation proves it.
- Do not make Hugging Face the only way to run recommendations.

## Current Context

The project already contains:

- A Next.js and Supabase app structure.
- A pure TypeScript recommendation engine in `src/lib/recommendation/engine.ts`.
- API validation and recommendation routing in `src/app/api/recommend`.
- Local champion, tier list, player, and build data under `data/`.
- Existing Python scripts and earlier Flask-era recommendation code.

The current TypeScript engine combines meta strength, player fit, counter context, bans, picked champions, and priority weighting. This is useful as a first expert label source for ML training.

## Recommended Approach

The first model should be a tabular ranking/regression model rather than a text model.

Each training row represents one candidate champion in one recommendation context. The model receives engineered features for that champion and context, then predicts a recommendation score. At inference time, all legal candidate champions are scored and sorted.

This approach is recommended because:

- Champion recommendation is mostly structured data, not natural language.
- Tabular models train quickly on local machines.
- The model can work with limited data.
- It is easier to debug and compare with the existing engine.
- The output can remain explainable.
- It is straightforward to package for Hugging Face.

Initial model candidates:

- `HistGradientBoostingRegressor` from scikit-learn.
- `RandomForestRegressor` from scikit-learn.

The implementation can start with scikit-learn. More specialized ranking libraries can be considered later if evaluation shows a real need.

## Input Features

The model should combine three groups of signals.

Player profile features:

- Candidate champion is in the player pool.
- Player games on candidate champion.
- Player win rate on candidate champion.
- Player confidence on candidate champion.
- Missing-pool indicator for guests or new users.

Draft context features:

- Role.
- Enemy picks.
- Bans.
- Candidate champion banned flag.
- Candidate champion already picked flag.
- Number of enemy picks.
- Matchup score when available.
- Matchup data completeness.

Meta features:

- Region.
- Tier.
- Candidate champion role.
- Candidate champion win rate.
- Candidate champion pick rate.
- Candidate champion ban rate.
- Candidate champion rank.
- Patch or data version when available.

Expert features for V1 training and comparison:

- Expert meta score.
- Expert player score.
- Expert counter score.
- Expert total score.

The target label for V1 is the expert total score produced by the existing recommendation engine.

## Model Output

The model returns:

- A score for each legal candidate champion.
- A ranked top N list.
- Lightweight explanation factors based on the input features and expert comparison.
- Warnings when data is missing or confidence is low.

The first version does not need perfect causal explanations. It should still expose the most useful signals, such as strong meta rank, strong player fit, useful matchup data, or missing matchup data.

## ML Directory Structure

Add a new `ml/` directory:

- `ml/build_dataset.py`: builds a tabular dataset from local JSON data and expert labels.
- `ml/train.py`: trains and saves the model artifact.
- `ml/predict.py`: loads the model and scores champion candidates for a context.
- `ml/evaluate.py`: compares ML output against the expert engine.
- `ml/features.py`: shared feature-building helpers.
- `ml/requirements.txt`: Python dependencies for training and Space runtime.
- `ml/README.md`: local training, evaluation, and publishing instructions.
- `ml/space/app.py`: Gradio app for Hugging Face Spaces.
- `ml/space/requirements.txt`: minimal Space dependencies.

The exact files can be adjusted during implementation if a smaller structure is cleaner, but training, inference, feature construction, and Space UI should remain separated.

## Data Flow

Training flow:

1. Load available champion stats, player pool samples, tier lists, and draft-like contexts from `data/`.
2. Generate candidate champion rows for each context.
3. Use the existing expert recommendation logic to assign target scores.
4. Build a tabular dataset.
5. Train a scikit-learn model.
6. Save the model artifact and feature metadata.
7. Evaluate top-k agreement with the expert engine.

Inference flow:

1. Receive role, region, tier, enemy picks, bans, and optional player pool.
2. Build one feature row per candidate champion.
3. Exclude banned or already picked champions before ranking.
4. Score legal candidates with the trained model.
5. Return top N recommendations with explanation factors.

Hugging Face flow:

1. Package the model artifact with the Space.
2. Expose inputs through Gradio controls.
3. Show ranked recommendations and explanation factors.
4. Document how to retrain and republish the model.

## Integration Plan

V1 keeps the ML system independent:

- Add the ML pipeline under `ml/`.
- Train and evaluate locally.
- Publish a Hugging Face model or Space.
- Keep the Next.js `/api/recommend` route on the existing TypeScript expert engine.

V2 adds optional app integration:

- Add an experimental API route such as `/api/ml-recommend`.
- Compare expert and ML recommendations side by side.
- Use the ML output only when the model artifact is available and healthy.

V3 improves training data:

- Collect real match outcomes by patch, region, tier, role, draft, and result.
- Mix expert labels with match outcome labels.
- Evaluate model behavior across patches.
- Retrain periodically when enough new data exists.

## Evaluation

Minimum V1 evaluation:

- Top-1 and top-5 agreement with the expert engine.
- Mean absolute error against expert total score.
- Ban and already-picked exclusion checks.
- Guest-mode prediction with no player pool.
- Prediction when matchup data is incomplete.

The V1 model is acceptable when:

- It produces stable rankings for common contexts.
- It never recommends banned or already picked champions.
- Its top-5 recommendations are close enough to the expert engine to be useful for manual testing.
- The Hugging Face Space can run from a clean environment.

## Error Handling

- If the model artifact is missing, scripts should fail with a clear setup message.
- If a context has no player pool, the feature builder should use explicit missing-player signals.
- If matchup data is missing, the model should receive a missing-data indicator rather than fabricated precision.
- If an unknown champion id is provided, prediction should reject the input or ignore it with a warning.
- If the Space cannot load the model, it should show a visible error instead of returning empty recommendations.

## Testing

Add focused tests for:

- Feature construction.
- Candidate filtering for bans and already-picked champions.
- Dataset generation shape and required columns.
- Prediction output ordering.
- Evaluation metrics on a small deterministic fixture.

Manual verification should include:

- Train locally from current data.
- Run local prediction for at least one role.
- Launch the Gradio app locally.
- Confirm the Space files are ready for Hugging Face.

## Open Decisions For Implementation Planning

- Whether to generate synthetic draft contexts only from current local data or add hand-authored fixtures.
- Whether the model artifact should live in the repository for early testing or be downloaded from Hugging Face.
- Whether to call the TypeScript expert engine from Python, port a matching label generator to Python, or export labels through a small Node script.
- Which exact Hugging Face publishing path to use first: model repository, Space repository, or both.
